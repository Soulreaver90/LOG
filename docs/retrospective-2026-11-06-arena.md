# Retrospective: the arena ending fight, v1 to v7

Written 2026-11-06, overnight, after the owner said: "So many mistakes, so many unknowns. Spend the time
figuring out everything... This took too many passes, building things that exist in vanilla."

Seven builds for one fight start. This page says why, with the evidence, and what changes.

---

## The one sentence

**Every defect in this run came from asking "how do I build X" instead of "where does this game already
do X".** The game had the answer each time. We wrote code instead of looking.

---

## The nine failures, each with its proof

### 1. We built the fight start without reading what we already knew

Bible row 930 held the vanilla fight-start tail, and the "put the camera near the actor first" rule, before
the arena work began. Four builds went out without either.

The owner: *"This is the 1000th time you built something without referencing what we already know/have.
Wasiting time and tokens."*

### 2. We inherited a bible row that was wrong, and built on it

The row at line 1579 said the player constructor is reachable from `ext 35`, `ext 38` and `ext 39`. Only
`ext 38` and `ext 39` reach it. The v6 brief told an agent to build on that row. The agent read the code and
refused, which is the only reason it did not ship.

**A wrong row labelled C is indistinguishable from a right one until somebody re-reads the code.** The bible
had no way to fail loudly.

### 3. We copied the one vanilla example that matched our architecture

Of the 35 vanilla records that raise a boss bar, **34 load no map**. We built our `battle_start()` helper
from `rom:0x3E9384`, the single one that does, because it matched the scene we had already designed. Then we
added a fade to cover the load, and the owner rejected it:

> "Why is it fading!??? Look at how EVERY OTHER FIGHT WORKS!"

We sampled one example. We never counted the population.

### 4. Our tools could not open our own builds

`scene_probe.map_entry` hardcoded the base ROM's map table and count. `map_view.py` inherited that through
one call. Neither could read map 6,100 at all, so for four builds nobody could look at the arena we shipped.
The failure was silent: the tool read the dead vanilla table and reported a normal-looking answer.

### 5. We trusted names over handlers

Cross-checking all 145 ext handlers against our own `EXT_OPS` table tonight: 50 of 54 agree, and **four of
ours are wrong**. `ext 23 visited` pops two values, not one. `ext 131`, `132` and `133` pop nothing at all;
they push a byte. They are getters, and we had them as setters taking an argument.

These were latent. Anyone encoding them would have produced a corrupt record.

### 6. We nearly reported our own measurement error as a finding

The first pass of the handler profiler disagreed with **22 of 54** known ops. Every one of those
disagreements was my bug, not the game's: `r0` stops being the VM stack at the first `BL`, so stores into a
freshly allocated struct look exactly like stack pops.

Validating the new method against the ops we already knew turned 22 false findings into 4 real ones.

> **A measurement that has not reproduced a known answer is not a measurement.**

### 7. We parked defects the owner could see

Backlog items 13 and 14 were both written on the morning of 2026-11-06, and both were still open when he
played v6 that night. Item 14 was also simply **wrong**: it blamed floor reflection art at y 200-223 for a
door that is actually a recess at cells (28-35, row 11).

A written-down defect he can see on screen is not progress.

### 8. We left a hole on purpose, from a misread quote

`battle_arena.py` line 117: `DOOR_MOUTH_ROW = 11  # left open on purpose: state 4 stands at (246,94)`.

He had stood **inside** the Capsule Corp alcove. The note recorded it as "in front" of the door, so the row
stayed open, and he walked straight in for three more builds. His own words named both halves of the bug:
*"its like I run into a wall, but I can walk into it"*, which is a closed row 10 above an open row 11.

### 9. Housekeeping hid his evidence from me

Seven `builds\mockups` folders for one mockup, where every other mockup has one. His save states were
scattered across them, and twice I told him I could not find states he had already given me.

## The three rules this run earned

1. **Count the population before copying an example.** "Vanilla does it this way" needs a number. One
   matching record is not evidence; 34 of 35 is.
2. **Validate a new measurement against known answers before trusting it on unknowns.** Had I shipped the
   first profiler pass, 22 wrong "findings" would have entered the bible as facts.
3. **Search the bible for what you are about to BUILD, not only for what you are about to read.** Rows 930,
   1037 and 1119 each already held an answer we spent a build rediscovering.

## Still open

- 4 wrong entries in `scene_lib.EXT_OPS` (ext 23, 131, 132, 133). Not fixed yet, because an agent is editing
  that file for v7. Fix after it reports.
- An audit of every other permanent tool for base-ROM constants that a build moves. Only the map table is
  confirmed fixed.
- A reverse index from each ext op to every vanilla record that uses it, so "does vanilla already do X" is a
  lookup and not a study. This is the artifact that would have prevented the whole run.
