## Section 4

| Fact | Tags | Label | Src | Id |
|---|---|---|---|---|
| **An animation row can be WRITTEN, not only borrowed.** A row is 4 u32 direction words at `set_header + 12 + 16 * 4 + 4 * 4 * anim`; each word names a record list of 12 byte records `{s8 dx, s8 dy, u8 w, u8 h, u16 attr0, u16 attr1, u32 frame header}`. Rows measured: `set:137` anim 9 `rom:0x391DAC` naming list `rom:0x38D944`, `set:103` anim 9 `rom:0x312724` naming `rom:0x30C380`, and the three NULL rows this work fills or leaves, `set:140` `rom:0x39D3D0`, `set:139` `rom:0x3B4820` and `set:104` `rom:0x31D950`. Filling one takes 4 raw type 0 frames of `8 + 1024` bytes, one 48 byte record list and the 16 byte row write, about 4.1 KB in the expansion area, and moves nothing | #sprite #form set:103 set:104 set:137 set:139 set:140 | C (row words and record bytes read in the base ROM and in the built dev master; `vegeta_zplus.write_anim_row`, two trial ROMs) | PWA | |
| **A record list appended to the expansion area needs a 12 byte stop after it, which a vanilla list gets for free.** The row word names only the first record, and `frames_of` finds the end by adjacency: `set:139`'s anim 21 list at `rom:0x39D2C4` is followed 48 bytes on by `set:140`'s own header at `rom:0x39D2F4`. An appended list has no such neighbour, so the next allocation can read as a fifth record, which is the same reader trap B0173 names on moved lists. Twelve bytes of `0xFF` stop it: `read_record` resolves no frame header and the walk ends. The game needs no stop, because its frame count is in code, not in the set (B0042, B0063) | #sprite #form #tool set:139 set:140 | C (record walk of both lists, 0xFF stop read back in both trial ROMs) | PWA | |
| **A written animation row must hold exactly as many records as the lending set's own row**, because the count is in code and not in the row. B0042 reads it out of the enter and tick pair for anims 0, 1 and 16 and labels the rest LIKELY; anim 9 is among the rest, so the four record count is taken from the four record rows of `set:137` and `set:103` rather than from a routine. `plan_anim_frames` raises when the drawn frame count and the lending row disagree | #sprite #form #open set:103 set:137 | L (count copied from the lending row; no anim 9 enter or tick routine was read) | PWA | |
| **Every anim 9 record measured carries the same geometry**: 32x32, `dx -8`, `dy -24`, `attr0 0x2000`, `attr1 0x8000`, in `set:103` anim 9, `set:137` anim 9 and the anim 21 rows of `set:104`, `set:139` and `set:140`. All five sets are OBJ slot `0x400`, which is exactly `32 * 32`, so a 32x32 frame is the largest one that fits | #sprite set:103 set:104 set:137 set:139 set:140 | C (`read_record` and `read_set` over both ROMs) | PWA | |
| **A set's geometry reference must be the TARGET set's own whole row, never the lender's.** `set:103` has a whole anim 9 and a NULL anim 21; `set:104` is the exact opposite. So a check written as "compare the new frames with the lender's revert row" would read four zero words on Piccolo and raise, while the same check against the target's own row passes | #sprite set:103 set:104 | C (anim 9 and anim 21 rows of both sets, base ROM and dev master) | PWA | |
| **B2388 holds for `set:140` and `set:104` only as far as their OTHER rows can show.** Their anim 9 rows are null, so there is nothing to read: what is measured is that their anim 21 rows name ONE list in all four directions (`set:140` and `set:139` both name `rom:0x39D2C4`, `set:104` names `rom:0x31D364`), and that the sibling sets 137 and 103 do the same for anim 9. One front view drawing is therefore the right shape for these two rows, but it is an inference from the neighbouring row, not a reading of the row itself | #sprite #open set:103 set:104 set:137 set:139 set:140 | L (anim 21 rows of all five sets; the anim 9 rows of 139, 140 and 104 are null and carry no evidence) | PWA | |

| **The dev master repaints exactly ONE shared OBJ palette entry**: index 172 goes from `(32, 208, 168)` in the base ROM to `(248, 200, 192)`, written by `art_inject` from `art\tables\palette.json`. A build may therefore only check the entries the frame actually USES: checking all 256 refuses good art over a colour it never touches | #palette #sprite #tool | C (256 entry compare of base against the built dev master, `art\tables\palette.json`, `to_indexed.frame_indices`) | PWA | |

| `to_indexed.frame_indices(src, want, pal, key)` is the ONE reader for a frame the owner drew, used by the command line tool and by every patch that puts his art in the ROM, so a build and a review refuse the same frame for the same reason. It returns `((w, h), one index per pixel)` and raises, naming the file, for an unknown colour, a part transparent pixel, a run time reserved index (0 is transparent and 168 is written at run time) or an indexed file whose palette disagrees with the ROM at an index the drawing uses. A near colour is never snapped, because a snapped pixel is his art changed without him seeing it | #tool #sprite #palette | C (`test_piccolo_powerup_art.test_it_refuses_a_frame_that_is_not_his`, both trial builds) | PWA | |
